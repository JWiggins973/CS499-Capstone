Software Design and Engineering

SNHU Apocalypse Game

What is the artifact?

The artifact is a text-based adventure game I originally built in 2024 in IT-140: Foundation in Application Development during my first year at SNHU. The player moves through rooms in a school, collects six items, and defeats Principal X to escape. The original version was a single procedural Python script that stored all room data in one dictionary and used console input and output for everything. There were no classes, no structure, and no way for a non-technical user to play without typing exact commands.

Why did I select it?

I chose this artifact because it had clear room for improvement through better software design. The original code worked but it was all in one file with no organization, making it difficult to read, test, or expand. Refactoring it gave me the chance to show that I can take messy working code and turn it into something well-structured and professional.

The biggest design improvement was breaking the script into three classes. The Room class manages exits and items for a single room. The Player class tracks where the player is and what they have picked up. The Game class ties everything together, handling movement, item pickup, win and lose conditions, and game reset. This separation means each piece can be understood, changed, and tested on its own without affecting the others.

I replaced all raw strings in the code with StrEnum constants for directions, room names, and items. Instead of typing plain text like "Library" or "N" throughout the code, the program uses defined constants like RoomName.LIBRARY and Direction.NORTH. This catches typos and inconsistencies in the source code immediately rather than allowing them to cause silent bugs at runtime.

Defensive programming is built into the design in several places. The Player's move method checks whether a direction exists in the current room's exits before allowing movement and returns False if it does not. The get_inventory method returns a copy of the inventory list rather than the list itself, so nothing outside the Player class can accidentally modify the real inventory. The GUI takes this even further by only showing buttons for valid rooms, meaning the user cannot submit an invalid command through the interface.

On top of the class structure, I built a Tkinter GUI that replaces the console entirely. The player sees the current room, available exits as clickable buttons, an inventory display, and a pickup button that only appears when there is an item in the room. I wrote unit tests across all three classes covering movement between rooms, inventory management, win and lose conditions, invalid moves, and game reset. I also organized the source files into a proper Python package called snhu_apocalypse, added a .gitignore, and added a requirements.txt so anyone can install the project dependencies in one step.

All planned outcomes were fully met

Outcome 1 — Building environments that help diverse audiences make decisions was met by replacing typed console commands with a point-and-click GUI. The original version required the player to know exact text commands. The enhanced version uses simple buttons that anyone can understand regardless of technical background, making the game accessible to a much wider audience.

Outcome 2 — Delivering professional-quality communications that are technically sound was met by writing clean and readable code throughout. Every class and method has docstrings explaining what it does. Variable names are descriptive and consistent. The code is organized into a proper package structure with clear file separation, making it easy for another developer to read and understand.

Outcome 3 — Designing computing solutions using sound practices while managing design tradeoffs was met by refactoring the single procedural script into three classes that each handle one area of the game. Using StrEnum constants instead of raw strings and returning copies of internal data rather than direct references shows attention to proper software design practices.

Outcome 4 — Using well-founded techniques and tools to deliver solutions that provide real value was met by building the Tkinter GUI using a standard Python library, writing unit tests to verify the game logic, and organizing the project with a .gitignore and requirements.txt. These are standard industry practices that make the project reliable, portable, and maintainable.

Outcome 5 — Developing a security mindset that anticipates problems and prevents them through design was met through defensive programming throughout the codebase. The move method validates direction input before acting on it. The inventory is returned as a copy so outside code cannot tamper with the real data. StrEnum constants prevent invalid values from being introduced in the source code. The GUI only displays valid options, removing the possibility of bad input at the interface level.

What did I learn?

The biggest thing I learned was how much easier code becomes to work with when it is broken into smaller pieces with clear responsibilities. In the original script, a small change to how rooms worked could break item collection or movement because everything was tangled together. After refactoring, I could change the Room class without worrying about the Player class, and I could update the GUI without touching the game logic at all.

The hardest part was connecting the three classes together. The original code used simple room name strings in the exits dictionary. After refactoring, each exit needed to point to an actual Room object instead of just a name. I solved this with a two-pass approach where I first create all the Room objects, then loop through again and replace the string references with the real Room objects.

Building the GUI came with its own challenges. Tkinter handles widget layout differently than I expected, and button styling behaves differently on Mac than on Windows. I had to research alternatives and adapt my approach more than once. Writing the unit tests taught me how to think about edge cases, like what happens when a player tries to move in a direction that does not exist, or what happens if someone tries to pick up an item in an empty room. Those tests gave me confidence that the refactored code actually works the way it should.

Algorithms and Data Structures

Course Planner

What is the artifact?

The ABCU Course Planner is a program I originally built in 2025 in CS-300: Data Structures and Algorithms. It loads course data from a CSV file and lets users search for courses and sort them. The original version was a command-line C++ program that most people outside of a computer science class would not know how to use.

Why did I select it?

I selected this artifact because the original implementation had clear room for improvement. Course lookups required scanning the entire vector at O(n), prerequisite validation used a set at O(log n), and an alphabetical quicksort ran at O(n log n) on every print request. There was no multi-level prerequisite traversal and no way to see what completing a course unlocks.

My goal was to push query times as close to O(1) as possible by restructuring the system around in-memory data structures. I replaced the vector and set with a single Map that brings all course lookups to amortized O(1). The alphabetical quicksort was replaced with a topological sort that runs once at startup at O(V + E), producing a single pre-computed list where every course appears after its prerequisites.

I built a recursive prerequisite chain using depth-first search that traverses prerequisite relationships in the Map at O(V + E) on the first click and returns every ancestor in dependency order. I added caching to store results and drop repeat lookups to O(1). The unlock path was fixed by building a reverse adjacency map during the same load step that populates the main Map, so dependents are already stored and each lookup runs at O(1) without needing to scan the full catalog.

On the security side I added a Content Security Policy to reduce the cross-site scripting attack surface, whitelisted all external resources, and used Angular's @Input({ required: true }) to enforce required data at compile time. The application was rebuilt from C++ into an Angular web application with color-coded course cards, real-time search with debounce, and a visual prerequisite chain. I also wrote unit tests covering lookups, chains, filtering, and topological ordering.

All planned outcomes were fully met

Outcome 2 — Delivering professional-quality communications that are technically sound was achieved by writing well-documented TypeScript code with clear method names, consistent formatting, and a component structure that separates the search, card display, and detail views into their own files.

Outcome 3 — Designing computing solutions using algorithmic principles while managing design tradeoffs was achieved in several ways. Replacing the vector and set with a Map improved lookup time from O(n) to amortized O(1) at the cost of higher memory for the hash structure. The topological sort replaced an alphabetical sort with an algorithm that solves the actual dependency problem at O(V + E) instead of O(n log n). The caching layer trades memory for eliminating redundant O(V + E) recursive traversals on repeat clicks.

Outcome 4 — Using well-founded techniques and tools to implement solutions that deliver real value was achieved by rebuilding the application in Angular 21 with recursive graph traversal algorithms that make the planner genuinely useful for course planning. Unit tests verify correctness across all service methods. The caching optimization was not part of the original plan but was added after recognizing inefficiency during code review.

Outcome 5 — Developing a security mindset that anticipates vulnerabilities was achieved by adding a Content Security Policy that restricts what the browser can load and reduces the cross-site scripting attack surface. All external resources are explicitly whitelisted. The .gitignore prevents sensitive files and build artifacts from being committed to version control. Angular's @Input({ required: true }) enforces required data at compile time, eliminating a category of runtime errors from missing inputs.

What did I learn?

The most difficult part was getting the recursive algorithms to produce correct results. On my first iteration the prerequisite chain displayed backwards because the recursion was appending courses in the wrong order. The unlock path had a similar issue where it recursively returned the entire downstream tree instead of just direct dependents. Fixing these bugs taught me the difference between code that runs and code that produces the right output. Building the reverse adjacency map to fix the unlock path also taught me when to fix a bug with a better data structure rather than just patching the logic. Once the algorithms were correct I added caching after spotting redundant traversals during code review. That progression from working to correct to optimized showed me that the first solution is rarely the final one.

Getting the development environment running was also a significant challenge. Angular 21 requires Node 18 or higher, but my system was running Node 10.23.0, which had been end-of-life since 2021. This caused syntax errors, missing platform binaries, and failed installs. I resolved this by switching to Node 20 through nvm. During package resolution, installing angular-cli-ghpages accidentally removed tslib, which broke every TypeScript file in the project. I fixed this by reinstalling the dependency. For deployment, I set up a GitHub Actions workflow that builds on Ubuntu with Node 22 and deploys to GitHub Pages automatically on every push.

Animal Shelter Dashboard

What is the artifact?

This artifact is an animal shelter dashboard I originally worked on in the summer of 2025 in CS-340: Client/Server Development at SNHU. It was built using Python, MongoDB, and Dash, and allows users at Grazioso Salvare to filter animal rescue data by rescue type and view results in an interactive table, map, and breed chart. The base dashboard code was provided as part of the class and the original version ran inside a Jupyter notebook within a Docker container.

Why did I select it?

I chose this artifact because it combines a database layer, backend module, frontend interface, and security considerations all in one project. The base code was provided as part of the coursework, so getting it to run required reading and understanding someone else's codebase, troubleshooting a broken environment, and tracing authentication errors across a Docker container and local Python environment before I could improve it. This is closer to real-world production work where developers inherit existing codebases and build on top of them rather than starting from scratch.

On the database side, I added indexes on animal_type and breed to improve query performance from O(n) full collection scans to O(log n) using MongoDB's B-tree structure. Without indexes every query checks every document in the collection sequentially. With indexes MongoDB maintains a sorted tree that lets it skip directly to matching records. I also added a compound index on both fields together so queries that filter by animal type and breed simultaneously can resolve through a single index lookup. I expanded the CRUD module from four methods to eight by adding count, create_many, update_many, and delete_many to handle real-world batch operations.

On the architecture side, I migrated from a Dash-based Jupyter notebook to a Flask REST API with a vanilla JavaScript frontend. The original had frontend and backend mixed in one file. The new version routes requests through a service layer that is the only code that touches the database through the CRUD module. Config.js is the only file that changes between projects, and the rest of the code is split into focused modules for table rendering, filtering, mapping, charting, forms, and API communication.

I addressed security by moving hardcoded credentials into a .env file, adding query sanitization through an allowlist that strips unauthorized fields before they reach the database, restricting browser origins through CORS, and checking that required fields are present before inserting records.

All five outcomes were fully met

Outcome 1 — Building collaborative environments that enable diverse audiences to support organizational decision making was met by designing the dashboard so that non-technical stakeholders like rescue coordinators and shelter managers can interact with the data through filters, charts, and maps rather than writing database queries. The reusable dashboard engine also supports collaboration by making it easy for other developers to adapt the same framework for different projects by editing a single configuration file.

Outcome 2 — Delivering professional-quality communications that are technically sound was met by cleaning up the codebase, removing dead code, writing clear comments, and organizing the project into separate backend and frontend modules. The code is structured so that another developer could read through any single file and understand its purpose without needing to reference other files.

Outcome 3 — Designing computing solutions using algorithmic principles while managing design tradeoffs was met by adding database indexes. The tradeoff is that indexes use additional disk space and slightly slow down write operations because the index must be updated on every insert or delete. Since this application reads far more often than it writes, the improvement from O(n) full collection scans to O(log n) indexed lookups is well worth the cost.

Outcome 4 — Using well-founded techniques and tools to implement solutions that deliver real value was met by expanding the CRUD module with methods that handle real-world batch operations, building a dedicated test file to verify all methods work correctly, migrating from a notebook-based Dash application to a proper Flask REST API, and designing a reusable frontend engine that can be configured for different datasets without rewriting code.

Outcome 5 — Developing a security mindset that anticipates vulnerabilities and ensures privacy of data was met through multiple layers of protection. Moving credentials to environment variables prevents sensitive information from being exposed in source code or version control. Query sanitization with an allowlist reduces the injection attack surface by stripping unauthorized fields before they reach the database. CORS restrictions limit which browser origins can make API requests. Required field validation checks that expected fields are present before inserting records.

What did I learn?

The biggest challenge had nothing to do with the code itself. Getting the environment set up in VS Code took significant troubleshooting. The original project ran inside a Docker container using Jupyter notebook, which meant MongoDB authentication was handled internally. When I moved to VS Code I was connecting from outside the container for the first time and kept getting authentication errors. I eventually figured out that I needed to add authSource=admin to the connection string to tell PyMongo where the user account was stored. That was frustrating but it taught me how MongoDB handles authentication differently depending on where the connection comes from.

Another challenge was that the original project was a Jupyter notebook file which cannot be run directly with Python. Converting it to a standard .py file made it easier to run from the terminal, manage with version control, and work with in VS Code like any other Python project.

I learned how to properly structure a Python project with environment variables, how database indexing works at a deeper level with B-tree structures, and how to expand an existing module without breaking what was already working. Building the reusable dashboard engine taught me how to think about separation between configuration and logic. By isolating everything project-specific into config.js I created something I can use again on future projects without rewriting the core code. That kind of reusability is something I had not prioritized before, and it changed how I think about building software.
